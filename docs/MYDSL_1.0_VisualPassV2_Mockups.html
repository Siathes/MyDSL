MyDSL 1.0 — Visual Pass v2

Title-bar polish + general Geyser UI refinement, built from the 5 existing theme presets. 2026-08-26, decided same day: §1.5 is the build — uniform, small/discreet, window-name-only header text (no "MyDSL —" prefix). Steven picked Direction A's look, then confirmed it needs to work on both Linux and Windows (ruling out Direction A's original one-line mechanism), then locked the final styling. §1, §2, §3 below stay in the doc as the reasoning trail, not as remaining options.

§0What the research actually found, before any mockup was drawn

Per docs/MyDSL_MudletWindowManagement.md and confirmed independently against Mudlet's own Geyser manual + the Qt docs it wraps — read this before judging feasibility, since it changes what "hide the title bar" can honestly mean here.

  • There is no native "hide title bar" call. A MyDSL UserWindow's title strip is Qt's own QDockWidget chrome, not something Geyser builds. Mudlet's UserWindow only exposes setTitle()/resetTitle() (change the text) and setStyleSheet() (restyle border + title area via CSS). Nothing removes the bar outright without dropping to raw C++ (setTitleBarWidget()), which isn't available from Lua.
  • The real lever is QDockWidget::title{} CSS, and this codebase has never used it. MyDSL.Theme.panelCSS() (MyDSL_ThemeEngine.lua:423) already returns a stylesheet applied to every UserWindow via setStyleSheet() — but it only sets bare, unscoped background-color/border/border-radius, never a QDockWidget::title block. That's the actual gap this pass closes: an additive rule inside a function that already runs for every window, not a new mechanism.
  • Two theme keys are already sitting there unused for this exact purpose. Every preset already defines titleColor and titleBgColor — but grepped directly, titleBgColor has zero real consumers anywhere in the codebase, and titleColor is only read by the 3 windows that hand-build their own in-content title label (LiveView, TickView, AlterformView), never by the native title bar itself. All 3 directions below spend that already-modeled, already-switchable data for the first time rather than inventing new theme keys.
  • You cannot fully remove the bar and keep drag/dock working — confirmed against the Qt forum thread on this exact question. Stylesheet-only hiding leaves the bar's hit area present but blank (title survives structurally, just invisible); the only way to truly delete it needs setTitleBarWidget(), and that kills the ability to drag/dock the window. Every direction below is a flavor of "flatten it to near-nothing," not "delete it" — full removal isn't on the table without giving up dragging, which nobody's asked for.
  • Nothing here goes near the resize/reflow bug. All directions below are pure stylesheet strings and/or plain Geyser Labels, added through paths already wired through WindowRegistry.lua's applyTheme(). No move(), no resize(), no new sysWindowResizeEvent handler — the exact class of change MyDSL_MudletWindowManagement.md documents as safe (a passive stylesheet), as opposed to the class that caused the original reset bug (active reflow on resize events).
  • Confirmed the same day, once cross-platform became a hard requirement: a second, smaller wrinkle surfaced in Mudlet's own GitHub PR discussion for the setStyleSheet() feature itself (Mudlet/Mudlet#4046) — one maintainer noted "the border styling won't be preserved if docked, the titlebar however does." That's about docked vs. floating, not OS, but it's relevant here since docking to a screen edge is a normal, expected MyDSL interaction: a window's border/radius theming may revert once docked, on any OS, while title-bar CSS keeps working when docked. Not independently re-verified against a live docked window from this read-only clone — flagged for Claude Code to spot-check once any direction below is actually built, not asserted as settled fact.
⚠ Platform finding that changed the recommendation, straight from Mudlet's own Geyser manual: setStyleSheet()'s title-area CSS on a UserWindow only reliably works on Linux — on macOS/Windows the OS theme draws the title bar and ignores most of this CSS (a well-known general Qt limitation on those two platforms, not a Mudlet-specific bug — corroborated by the wider Qt community, not just Mudlet's own docs). This only affects the native title bar's own color/text styling — the window body's background/border/radius theming is separate CSS that already ships and works fine on every OS today. Since Steven needs this to work on both Linux and Windows, Direction A exactly as drawn below is not viable as its own implementation — see §1.5 for how to get the same look without depending on it.

§1Direction A — Quiet Chrome (Linux-only as designed — kept for reference, see §1.5)

Steven picked this look. As originally designed: native title bar stays exactly where and what it is — still draggable, still dockable — but its background blends into the window body and its text picks up the preset's own titleColor instead of the OS default grey/white. One new CSS block inside panelCSS(), nothing else changes. Kept below exactly as first drawn so the visual target is clear — but per §0's platform finding, this exact mechanism only renders on Linux. §1.5 delivers this same look in a way that actually works on Windows too.

§1.5Direction A+ — Quiet Chrome, Cross-Platform (decided — this is what gets built)

Final spec, confirmed by Steven: uniform across every window (no mixing in Direction B's bolder style anywhere), small and discreet, and the header text is just the window name — no "MyDSL —" prefix, since every window in this addon is already understood to be a MyDSL window. Mechanism unchanged from the proposal: the real title bar is flattened to a blank hairline sliver (kept alive purely so drag/dock still works), and a plain Geyser.Label — an ordinary widget, not native window chrome, so it styles the same on every OS — sits just under it carrying the quiet themed title. Same code path as §2 below, just styled quietly and named plainly.

§2Direction B — Zero Chrome, Custom Header (not chosen — Steven went uniform/quiet, kept here as the mechanism source §1.5 is built from)

Goes further than §1.5 stylistically: same flatten-the-native-bar-to-a-sliver-plus-Label mechanism, but the Label is bold, all-caps, and uses titleBgColor as a visible fill rather than a near-invisible tint — the same pattern MyDSL_LiveView.lua, MyDSL_TickView.lua, and MyDSL_AlterformView.lua already use for their own titles, just extended to every window instead of 3, and turned up visually instead of down. This is the first real use of titleBgColor anywhere in the codebase at this strength.

Final decision — build spec

  • Mechanism: §1.5, not Direction A's original one-liner — confirmed both Linux and Windows need to work, and native title-bar CSS (Direction A/C as first drawn) only renders on Linux. Real title bar flattened to a blank sliver (drag/dock only, no visible chrome); a plain Geyser.Label underneath carries the visible title, since Labels style identically on both OSes.
  • Coverage: uniform — every window gets the same treatment. No mixing in Direction B's bolder style anywhere.
  • Weight: small and discreet, matching §1.5's mockups above (10.5px, low-opacity tint background, no bold/all-caps) — not Direction B's bold filled header.
  • Header text: window name only — "Combat", "Affects", "Scan", etc. No "MyDSL —" prefix on any window.
  • Not part of this decision, still worth Claude Code's attention: the docked-window border-styling caveat from §0/Mudlet's own PR discussion, worth a spot-check on a real docked window once this is built (unverifiable live from this read-only clone). Direction C's per-zone coloring is explicitly not being built now — dropped, not deferred, since Steven chose uniform.

Full technical grounding, file/line references, and the leftover titleBgColor dead-key finding are also written into HANDOFF.md's Claude Desktop section for Claude Code.
